- (direction by user) Have the LLM first check whether the user-provided quiz topic makes sense before generating the quiz
- (technique) Selected batch: Job to Be Done, Assumption Reversal, Role Playing, Decision Tree Mapping
- (idea by coach) The pre-check may be hired to protect quiz quality and save the user from a bad generation without making them defend or rewrite their idea
- (idea by user) The topic check should ensure the system can generate real questions
- (insight by coach) Real questions implies the topic is coherent, sufficiently specific, answerable, and capable of supporting meaningful quiz content rather than plausible-sounding filler
- (insight by coach) The first gate is topic viability: distinguish meaningless input such as ???, 123, or abc from a real but possibly underspecified concept such as family
- (idea by user) Inputs like ???, family, 123, and abc should be recognized as unable to serve as usable quiz topics
- (direction by user) The core requirement is a topic viability gate before quiz generation; the family example is withdrawn as a bad example
- (idea by coach) The gate should not prove that a topic is excellent or factually correct; it should establish enough semantic signal that a responsible quiz attempt is possible
- (technique) Started Assumption Reversal
- (idea by coach) Do not ask whether the topic is good; ask whether it is quizable, meaning the system can identify a subject and produce grounded question ideas
- (idea by coach) Require the validator to restate the proposed quiz topic in one sentence before generation; an incoherent restatement fails the gate
- (idea by coach) Have the validator draft three candidate questions internally and reject or clarify when it cannot do so without guessing
- (idea by coach) Split the gate into cheap input checks for empty or gibberish strings and an LLM check for ambiguous or underspecified topics
- (idea by coach) Replace a hard rejection with a rescue prompt that explains the problem and gives examples of usable topic phrasing
- (idea by coach) Return a viability reason such as empty, gibberish, too vague, unsupported, or ready instead of exposing only a yes-or-no result
- (idea by coach) Let the gate offer a best-effort interpretation for borderline input, but require the user to confirm it before quiz generation
- (technique) Switched to Role Playing
- (idea by coach) From the unusable-input user perspective, the gate should fail forward with a clear explanation and an immediate path to enter a usable topic instead of showing a generic error
- (idea by user) When the viability gate rejects the input, the user should enter a new topic
- (insight by coach) An invalid topic should stop generation and return the user to the topic-entry step for immediate replacement
- (question by user) Asked for the UX pros and cons of preserving rejected text versus clearing the topic field
- (idea by coach) Recommended UX: preserve rejected text, focus the topic field, and select its contents so typing immediately replaces it; clear only through an explicit user action
- (decision by user) Adopt the UX where rejected topic text is preserved, focused, and selected for replacement; clearing is explicit and the UI provides recovery guidance
- (idea by coach) The validator should return a small structured result such as viable, reason, user message, and optional suggested topic; the UI should own presentation and field behavior
- (decision by user) Keep the validator simple: it only identifies whether the topic is viable or not
- (direction by coach) Use a minimal boolean viability contract; keep rejection messaging, focus behavior, and retry handling in the application layer
- (direction by user) Proceed to define the minimum condition for a topic to be considered viable
- (idea by coach) Minimal viability means the input is non-empty, not obvious gibberish, names a recognizable subject or activity, and can support at least one meaningful question without invented context
- (decision by user) Accept minimum viability rule: input is non-empty, not obvious gibberish, names a recognizable subject or activity, and can support at least one meaningful question without invented context
- (technique) Started Decision Tree Mapping
- (insight by coach) The core decision tree is binary: viable proceeds to quiz generation; nonviable stops generation, preserves and selects the topic text, shows recovery guidance, and loops back for a new topic
- (direction by user) Rejected the proposed shorter-quiz or different-topic fallback when validation passes but generation cannot produce enough meaningful questions; desired handling remains unspecified
- (direction by user) If viable topics too often fail to produce enough meaningful questions, adjust the viability check based on those recurring failures
- (technique) Completed Decision Tree Mapping
- (insight) Wrap-up synthesis: run a boolean topic viability check before quiz generation. Viable means non-empty, not obvious gibberish, a recognizable subject or activity, and able to support at least one meaningful question without invented context. If not viable, stop generation, preserve and select the entered topic, show recovery guidance, and let the user replace it. If repeated generation failures occur after approval, tune the viability check based on those cases.
